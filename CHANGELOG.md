# Changelog

## Unreleased

- Taught every tool in the package to read Geomview **VECT**, and added VECT output to **Convert XYZ...** and to a new `--convert` command line. Bumps Curve It to **V3_10**. VECT is the polyline format Geomview reads and that ridgerunner and the knot-theory tools around it write, and it is the only curve format here that states whether each component is a closed loop, in the sign of its vertex count. Reading is universal; writing is deliberately confined to the converter, so the generators still emit coordinate XYZ and there is exactly one place to go to change format.

- Fixed silent corruption, which is what "no VECT support" actually meant before this. Every reader in the package treated an unrecognised file as coordinate rows and took the first three numeric tokens of each line, so a VECT file parsed without complaint into the wrong curve: `7.7.vect`, a 91-vertex closed knot, came back as 93 points whose first row was `[1, 91, 1]` — the `NPolylines NVertices NColors` line — and whose last was `[1, 0, 1]`, the leading three channels of the trailing magenta RGBA. It now reads as 91 points. Asking for the coordinate or molecular reader explicitly on a VECT file is refused with that reason named, rather than served.

- Put the parser in one place, `curve_it_lib/vect_io.py`, imported by the others through the same relative-then-flat fallback `svg2xyz.py` already uses for the shared resampler, and soft everywhere: a missing `vect_io.py` costs the VECT format and nothing else. Three properties of real files drive it, each measured against the 396 files ridgerunner leaves in `~/.local/share/ridgerunner` rather than assumed. `#` starts a comment that runs to end of line and sits anywhere, including trailing a coordinate row — `simple_clasp.vect` marks constraint-pinned vertices that way — so comments are stripped before the file is split rather than by skipping whole lines. Count lists may wrap across lines, so the file is read as a token stream and not line by line. And a negative vertex count means closed: every knot in that corpus is negative, and the one file holding open arcs, `simple_clasp.vect`, is positive at `33 38`. All 396 files read, and write back and re-read with geometry equal to 1e-8 and colours to 1e-6, across 578 closed and 2 open components, 11 of them carrying one colour per vertex and 4 carrying none.

- Confirmed that the closed-component convention already matches. A closed VECT component does not repeat its first vertex; over that corpus the gap from last vertex back to first runs 0.83 to 1.02 of the median step, one ordinary segment. That is the same invariant Curve It's own curve files hold, so geometry crosses between the two formats with no dedupe pass, and a closed curve handed to the writer with its first point repeated has the repeat removed — compared on the rounded rows that will be written, not on a geometric epsilon, since it is the written text a later reader sees.

- Let the file answer the question it is the only one able to answer. A VECT input now supplies `--path-type` in Curve It and Get phase, `--closed` in XYZ to 3D Model and Interpolate, the drawn closure in View curve, and `--closed-chains` in Plane It — where its polylines become chains `A`, `B`, `C` and its closure fills in exactly what `LINK` records fill in for a PDB. An explicit option always wins, which is what the sentinel defaults are for; `interpolate_xyz.py` gains `--open` and `view_xyzV3.py` gains `--closed` so that each has a way to say both things. A selection mixing closed and open components is reported and left open rather than silently rounded either way. Measured on the torus-knot fixture: reading it as VECT produces all 6888 `ATOM` records byte-for-byte identical to reading the same curve as XYZ with `--path-type closed`, and `XYZ to 3D Model`'s `auto` closure, which was right by luck on `simple_clasp.vect`, is now right by statement.

- Stopped two writers handing a `.vect` name to a body that is not VECT. Curve It's `_rescaled` sidecar and `interpolate_xyz.py`'s `_interpolated` output both derive their extension from the input and both always write plain coordinate rows, so a `.vect` input produced a file named VECT that no VECT reader could open. Both now fall back to `.xyz`.

- Added `--convert INPUT OUTPUT` to `curve_it.py`, the command-line form of **Convert XYZ...** and the only place the package writes VECT. The output format comes from the extension — `.vect` writes VECT, `.pdb` a fake PDB, and `.xyz`, which cannot settle between the two XYZ forms on its own, writes molecular unless told otherwise. `--convert-closed` takes `all`, `none`, a selection such as `A,C`, or `auto`, which believes a VECT input and otherwise writes components open rather than guessing from geometry; it feeds VECT's vertex-count signs and fake PDB's `LINK` records alike, since they record the same fact. `--convert-color` takes one colour per component as a name, `#hex`, or 3-4 numbers, cycling when there are fewer colours than components. Colours are read and reported everywhere but are not geometry, and no other format here can hold them, so they are stated to be lost through anything that does not end in VECT.

- Reported what the file says instead of leaving it implicit: component counts and closure appear in the Convert dialog's preview line, in `xyz2model`'s load summary, and in a `[INFO]` line wherever a stated closure overrides a default. The Convert dialog fills **Closed components** in from a VECT input's own header, and only while the field still holds what it filled in last, so a typed value is never overwritten.

- Fixed the z axis being drawn short in every 3D preview in the package. `set_equal_aspect_3d` in `view_xyzV3.py`, which **View curve** uses, gave all three axes the same data range but left the axes box at Matplotlib's default aspect of `(4, 4, 3)`, so a curve with equal extent in x, y and z rendered with its z direction at exactly 0.75 of the other two. Measured on a unit cube under an orthographic view down each axis, the rendered `z/x` and `z/y` ratios were both `0.7500` before and are both `1.0000` after. Squaring the box off with `set_box_aspect((1, 1, 1))` was the missing half of "equal aspect"; the limits alone were never enough.
- Applied the same correction to the other two 3D previews, which had neither equal limits nor a cubic box: Curve It's built-in fallback viewer, used when `view_xyzV3.py` cannot be imported, and the 3-D panel of **XYZ to 3D Model**'s preview, whose three flat panels were already `set_aspect("equal")` while the 3D one was not.
- Replaced an `ndarray.ptp()` call with `np.ptp()`, which NumPy 2.0 removed from the array class.

- Made **SVG to XYZ**'s `auto` sampling actually automatic and made it the default, bumping the tool to **v1.1**. `auto` previously meant "do not resample": the GUI field said `auto`, `optional()` mapped it to `None`, and `prepare_curves` then skipped resampling entirely, so the word promised a choice the tool never made. It now works a point count out from the curve's own geometry. For a chord `h` across a bend of radius `R` the gap to the true curve is about `h^2 / (8R)`, so holding that at the flattening tolerance gives `h = sqrt(8 * R_min * tolerance)` and `n = ceil(contour_length / h)`, per curve. On the shipped sample drawing at the default tolerance the star resolves to 159 points at 1.533 spacing; at tolerance 0.5 and 0.005 the same curve gives 50 and 501. A unit circle at tolerance 0.05 resolves to 10 points whose worst sagitta is 0.0489, just inside the bound.
- **This changes default output for every existing script and GUI run.** `--points keep` restores the previous behaviour exactly, and is verified against a golden file built from the old code. The reason recorded for that old default, that keeping the flattened points "places a point exactly on every corner", is now served by corner pinning instead: resampling reproduces every vertex sharper than `--min-corner-angle` exactly, so corners survive all three settings. What the old default really produced was uneven spacing: on the sample star the flattened segments run 0.030 to 12.590 units, a factor of 420, with nothing in the output saying so.
- Added `keep` as an explicit setting for the old behaviour, with `none`, `off` and blank as aliases, and taught `-n/--points` to accept a whole number, `auto`, or `keep` rather than only an integer. Added `auto` to `--spacing` as well: where `--points auto` resolves a chord per curve, making every curve equally accurate, `--spacing auto` resolves one chord for the whole drawing from its tightest bend, making every curve equally dense. On the sample drawing the first gives 159 and 154 points to the two components and the second gives 158 and 314, both at 1.543 spacing.
- Tracked whether points and spacing were each set explicitly, rather than merely non-empty. Now that `points` defaults to `auto` it always holds a value, so the previous collision check would have rejected every run that set a spacing, and the CLI would have let the points default silently outrank an explicit `--spacing`. An explicit spacing now outranks the points default, and only supplying both is an error.
- Excluded two kinds of vertex from the radius that drives auto sampling, because both are artifacts rather than curvature. A stub segment left behind by a drawing program fabricates a very tight bend: on the sample star a single 0.030-unit closepath segment reports `R_min = 0.985` against a circle-fit truth near 6.3, which would have made auto over-sample by the square of that error; requiring both adjacent segments to reach a quarter of the median recovers 5.938. A genuine corner is not curvature either, and is reproduced by pinning rather than by density, so letting one set the chord would inflate a plain 60-by-40 rectangle from 4 points to 59. With both exclusions the rectangle stays at 4.
- Applied the same stub rule to corner detection inside SVG to XYZ, which corrects a claim made in the entry below. The two 35-degree turns on the shipped sample star are not corners at all: they are the two ends of that 0.030-unit closepath stub, an eighth of the median segment length. Pinning them preserved the stub and defeated even spacing. Excluding them leaves the sample star with no corners, which is the truth about that drawing, and the earlier measurement of corner pinning "recovering" 1.216 radians of total curvature on it was measuring the artifact. Pinning's real value is unchanged and is now demonstrated on curves that have genuine corners: an irregular sharp 10-vertex star resampled to 137 points loses 1.98% of its contour length blind and 0.0000% pinned.
- Reported the resolved sampling rather than choosing invisibly, which was the same class of defect as the old silent default. `describe()` gains a `SAMPLING` block and the XYZ header records both the mode and, per component, the resolved count and spacing. The 420-fold spread above would have been visible in the file had this existed.
- Noted plainly in the CLI help, the GUI help and the README that auto matches the *drawing's* accuracy and knows nothing about what the curve is used for afterwards. At the default tolerance the sample star resolves to 1.542 units, which is 3.62 Angstrom once Curve It scales it to a 168-bp B-DNA contour, coarser than the 3.40 Angstrom helical rise. That is the right answer to "represent this drawing faithfully" and the wrong one to "sample finely enough to carry a transport frame", so a downstream resolution requirement still needs an explicit count or spacing.
- Reconciled the help text that predated corner pinning. The `points` entry no longer advises preferring `auto` "for polygonal drawings" on the grounds that a resampled corner is approximated, and the `corner` entry no longer claims it "has no effect when points per curve is 'auto', because nothing is resampled then", which stopped being true the moment auto started resampling.

- Moved even arc-length resampling into `curve_it_lib/interpolate_xyz.py` as `resample_curve`, `even_points`, `allocate_points` and `corner_flags`, and had SVG to XYZ import them. Curve It's `--interp-mode n` and SVG to XYZ were two implementations of one algorithm: on the same closed 3D polyline they agreed to `9.9e-09`, and to `5.7e-14` once the epsilon below was removed. `--interp-mode p` inserts points between existing ones and preserves the original uneven spacing, which the even resampler cannot express, so it is deliberately left alone and is byte-identical.
- Generalized the shared resampler to any number of dimensions and fixed a silent bug in the process: SVG to XYZ's `_even_points` returned an `(N, 2)` array for `(N, 3)` input, dropping z with no error, so a space curve would have been quietly flattened. The merged helper preserves every coordinate column and raises on input that is not `(N, D)`.
- Removed an epsilon from the denominator of `sample_curve_position` in both `interpolate_xyz.py` and `curve_it.py`. Computing `t = (s - s0) / (s1 - s0 + eps)` biases every interpolated sample toward the start of its segment; a zero-length segment is now guarded explicitly instead. The `curve_it.py` copy has the wider reach, because `reparameterize_closed_curve` implements `--path-start` and runs on every closed-curve job whatever the interpolation mode, so this bias was in essentially all Curve It output. It is four to five orders below the written precision: a `--path-start 0.37` run over 6888 atoms is byte-identical before and after. The duplicate copy is kept on purpose, with a comment saying why: `--path-start` must keep working when the optional `interpolate_xyz` helper is absent.
- Added `--min-corner-angle` to Curve It, defaulting to `20` from the shared constant so the two tools cannot drift apart, with a matching GUI field, help topic, CLI echo and PDB `REMARK` provenance line. **`--interp-mode n` now keeps corners instead of clipping them.** The compatibility position is measured, not assumed: `--interp-mode` still defaults to `none`, so most runs never reach this code; on smooth densely sampled curves no vertex reaches 20 degrees, so pinning takes the same code path as blind resampling and the output is bitwise identical, verified on three tutorial BR ellipse components and a torus knot; on coarse polygonal curves the output changes only toward higher fidelity, with a 12-gon and a sharp 10-vertex star both holding contour length exactly where blind resampling loses 0.12% and 1.98%; and `--min-corner-angle 0` reproduces the previous output byte-for-byte, verified on a 6888-atom PDB. No existing flag changes name, default or meaning.
- Bumped Curve It to `V3_9` and SVG to XYZ to `1.1`. The tool version travels in the XYZ header, so a file's provenance shows which sampling built it.

- Added **KnotPlot to XYZ** at `curve_it_lib/kp2xyz.py`, a knot and link importer that turns the catalogue shipped with a local KnotPlot installation into coordinate XYZ/txt curve files. A target is named the way KnotPlot names it, `4.1` or `6.3.2`, or given as a generator command such as `torus 2 3`, and each one becomes a file of plain `x y z` rows with every component of a link written as its own blank-line-separated block, addressable as components `A`, `B`, `C`, and so on. `--split` writes one file per component instead, `--list` prints the catalogue, and `--all` converts all of it in one pass.
- Extracted coordinates by driving KnotPlot headlessly rather than by parsing its files. A shipped catalogue entry is KnotPlot's own binary format, an ascii header beginning `KnotPlot 1.0` followed by chunked binary fields: `compAttr` and `endf` in all 585 entries, the coordinates in `LOCS` (471 entries) or `LOCF` (113, with `0.5.1` alone carrying neither), and `META` or `NAME` in a few dozen. There are no text coordinates to read, so the supported route is KnotPlot's own `coords` command. The tool writes a short `.kps` script that loads the target, optionally refines it, calls `coords`, and quits, then runs `KnotPlot -keepdir -nographics -stdin` against it. `-keepdir` is passed so that KnotPlot cannot chdir away from the folder the subprocess was started in and drop the extracted files somewhere else; on the build tested here, macOS 2025 June 2 under `-nographics -stdin`, `pwd` reports the given folder with or without the flag, so the flag guards the failure mode rather than fixing an observed one.
- Worked around the `coords` filename restriction. KnotPlot refuses an output name whose first character is `/` or `.`, so an absolute path fails with `` *** illegal character `/' in file name `` and writes nothing, while a plain relative name such as `sub/raw.txt` is accepted. That message carries a backtick before the character and a straight apostrophe after it, which is how it has to be spelled to be found in a log. The generated script therefore names bare `rawNNNN.txt` files only and the subprocess runs in a private temporary folder; this tool reads those dumps and writes the finished curve files into the requested output folder itself, so an `-o` path of any depth still works.
- Used `refine nbeads N` for `--nbeads` rather than the bare `nbeads N`, which KnotPlot deprecates in favor of it. The count is the total over the whole conformation and not a per-component figure: `--nbeads 300` on the three-component link `6.3.2` returns components of 107, 97, and 95 points.
- Deduplicated the catalogue by content hash, never by name, before listing or converting it. `basic` holds 585 knot and link files and 522 of them are distinct, so the listing and `--all` cover 522 entries and `--no-dedupe` keeps all 585. A full extraction of the 522 writes 59877 points in about 0.3 seconds, since one KnotPlot session serves every target instead of one session per target.
- Kept both spellings of a name whenever the two files differ, because the dotted and underscored entries are not merely aliases of each other, and the difference is chirality. 93 names ship in both spellings, but only 63 of those pairs are byte-identical; those 63 collapse onto the dotted form KnotPlot's own `load` syntax uses. The other 30 pairs are two different curves, and both are kept. 28 of the 30 are mirror images, the two chiral forms of one knot type: measured with `curve_it_lib/cal_xyz_total_curvature_writheV2.py` at its defaults, `8.19` gives `-8.62647841209301` and `8_19` gives `+8.62647841925399`, equal in magnitude to eight significant figures and opposite in sign. Reading either one as a redundant copy of the other would silently flip the sign of every chiral quantity computed from it, which is why content hashing was chosen over name matching in the first place. The remaining two pairs, `9.20`/`9_20` and `9.35`/`9_35`, share a handedness, and they are two slightly different conformations of one knot rather than one conformation stored in a different orientation: the same tool gives `9.20` `+6.346643502580359` against `+6.346635731949251` for `9_20`, and `9.35` `+7.539209051573574` against `+7.539218781711285` for `9_35`. Rotating or translating a curve leaves its writhe alone, so same-signed writhes that still differ rule out a re-orientation; their bytes differ as well, and the hash keeps them apart too.
- Added an opt-in reflection, so either handedness is available even where the catalogue ships only one. `--mirror` writes the mirror image in place of the original, `--both` writes the original and the mirror, and `--mirror-axis {x,y,z}` chooses which coordinate is negated, `z` by default. Exactly one coordinate is negated, because negating one axis is a genuine reflection while negating two composes into a rotation and leaves the handedness untouched. `z` is the default because it leaves `x` and `y` alone: the projection seen down the `z` axis is identical while every crossing swaps over for under, which is the mirror of the textbook knot diagram. Reflection negates the writhe, the linking number, and every other chirality-sensitive invariant, and it is applied to a whole link at once, so the components of a mirrored link stay in register with one another. Mirroring the shipped `8.19`, whose writhe is `-8.62647841209301` by the same tool, reproduces `+8.62647841209301` and so matches KnotPlot's own chiral partner `8_19`, `+8.62647841925399`, to eight significant figures. For an amphichiral knot such as `4.1`, whose shipped conformation measures `+0.15240866875536058`, near zero beside the `8.6` of `8.19`, the mirror measures `-0.15240866875536058` and is the same knot type in a different conformation, not a second knot. A reflected file is written as `<stem>_mirror.xyz`, or `<stem>_mirror_A.xyz` per component under `--split`, and its `#` header records that the coordinates were reflected and on which axis, so a file on disk is never ambiguous about its handedness. `--both` is opt-in rather than the default because `--all --both` writes 1044 files instead of 522. Callers get the same three choices as `extract(..., mirror=False, mirror_axis="z", both=False)`, with `mirror_points(points, axis="z")` reflecting one curve on its own.
- Exported every conformation exactly as KnotPlot ships it. The tool does not relax, tighten, or smooth the geometry; the only coordinate changes it makes are the opt-in reflection above, the opt-in `--nbeads` resampling, and the `--precision` rounding applied as each value is written, and none of them reshapes the curve. Resampling does move the points, though, so it is not a no-op even at the shipped count: `3.1` ships 47 points, and `--nbeads 47` shifts them by up to `0.096853` in a single coordinate and changes the writhe from `+3.3722171577968423` to `+3.3710769510513137`, both measured with `curve_it_lib/cal_xyz_total_curvature_writheV2.py` at its defaults. These are correct representatives of their knot and link types but are not ideal or ropelength-minimizing shapes, so their length, curvature, and writhe should not be read as ideal-knot values. Relaxation belongs in KnotPlot itself, before an export, and is not offered as a conversion option.
- Wrote the closed curves without repeating the first vertex, matching the convention Curve It, its writhe calculation, Generate SC, and SVG to XYZ already share. Whenever a written file holds more than one component, the report closes with the same `USING THIS FILE IN CURVE IT` block SVG to XYZ prints: a warning that Curve It concatenates all components by default, and the exact `--curve-components` command for the file's components, spelled out for the first three and closing by naming the last when there are more than three. A single-component knot, and every file written by `--split`, leaves nothing to choose between and so gets no block.
- Added cross-platform installation discovery that probes, in order, an explicit `--knotplot` path, the `KNOTPLOT` environment variable holding the full path of the executable, `KNOTPLOT_HOME`, the `knotplot`, `KnotPlot`, and `knotplot.exe` names on `PATH`, and the default install locations for macOS, Linux, and Windows. `--check` prints what was found and the search that found it, then launches the binary and looks for KnotPlot's own startup banner, so an executable file that is not KnotPlot is reported as exactly that and the exit status is nonzero; when nothing is found the message names the `KNOTPLOT` override, lists every location probed, and points at https://knotplot.com/download/ rather than failing with a bare file-not-found.
- Documented that KnotPlot's `torus p q` does not order its two indices the way every text does. Measured, `torus p q` winds the curve `p` times around the `z` axis and `q` times around the tube, so `torus 2 3` goes twice around the axis and three times around the tube. The common parametrization names that the `(2,3)` torus knot, while sources that put the winding around the tube first, including Adams' *The Knot Book*, call the same curve `(3,2)`; a `(p,q)` from a paper may therefore be `torus q p` here. The knot type is unaffected because `T(p,q)` and `T(q,p)` agree, but the shape is not: `torus 2 3` shows 3 crossings looking down `z` and `torus 3 2` shows 4, two presentations of one trefoil. The report prints a `TORUS INDEX ORDER` note whenever a `torus` target is used, a new `torus` help topic carries the detail with worked examples, and the GUI labels the entry field with the winding convention.
- Fixed a generator command typed without quotes being split into separate targets. `torus 2 3` is what KnotPlot itself takes and what anyone types, but both the GUI target field and `argv` split on whitespace, so it arrived as the three targets `torus`, `2` and `3`; each failed to load and the run produced nothing. `merge_generator_commands` now rejoins a bare generator with the arguments it requires, for `torus`, `lissajous` and `2lissajous` and their short spellings, in both the GUI and the command line. Only the required arguments are absorbed, because a catalogue name such as `4.1` also parses as a number and a greedy merge would swallow the following target: `torus 2 3 4.1` is the torus knot and then `4.1`. A token that already contains a space came from quoting and is left alone, so the quoted form keeps working, and an incomplete or non-numeric command is passed through for KnotPlot to complain about rather than guessed at.
- Fixed Preview reporting `there is nothing to preview yet - extract first` after an extraction that had in fact just run and failed. It now prints what KnotPlot said about each target, so a misspelled name reads as a misspelling.
- Added **Preview**, which extracts the current targets into a temporary folder and opens them in Curve It's own 3D curve viewer, `curve_it_lib/view_xyzV3.py`, without writing to the output folder, so a knot can be inspected before it is kept; `--preview` does the same after a command-line run. The viewer ends in a blocking `plt.show()`, so each curve is opened as a separate process: the tool window stays usable and several curves can be compared at once. At most 6 windows open per run and a larger run reports how many files it left on disk. Preview is enabled and disabled by exactly the same installation check as Extract, and a viewer that cannot start is reported without failing the extraction that succeeded.

- Added **SVG to XYZ** at `curve_it_lib/svg2xyz.py`, a 2D drawing converter that reads an SVG and writes a coordinate XYZ/txt curve file with a constant `z`, `0` by default. Every drawn `<path>`, `<polyline>`, `<polygon>`, `<line>`, `<rect>`, `<circle>`, and `<ellipse>` becomes one component, so a drawing holding several curves produces a curve file holding the same number of space curves, addressable as components `A`, `B`, `C`, and so on. The tool needs only `numpy` and the standard library; `matplotlib` is imported lazily and only for the optional preview.
- Implemented the full SVG 1.1 path grammar with a command-aware scanner rather than a number-list tokenizer, so that elliptical-arc flags are read as single characters and the unseparated form `a5 5 0 0110 0` emitted by SVGO parses correctly. Implicit command repetition, the `M`-to-`L` promotion of extra moveto coordinate pairs, the `S`/`T` control-point reflection rules and their reset on any other command, the retention of the subpath origin across `Z`, and the `1.5.5` two-number tokenization are all handled. Malformed data ends the parse, keeps every subpath read up to that point, and is reported as a note instead of discarding the file.
- Implemented the endpoint-to-center arc conversion of SVG 1.1 appendix F.6.5 together with the F.6.6 out-of-range corrections: coincident endpoints omit the arc, a zero radius degenerates to a straight line, radii are taken absolute, and radii too small to span the endpoints are scaled up by `sqrt(Lambda)`. Arcs, circles, ellipses, and rounded rectangles are all built from a single center-parameterized routine that emits cubic pieces of at most 45 degrees, holding the radial error near `2e-5` of the radius rather than the `3e-4` of the usual four-quarter constant; a measured unit-radius circle now deviates by `4.2e-6`.
- Composed group and element transforms exactly for `matrix`, `translate`, `scale`, `rotate` with and without a center, `skewX`, and `skewY`, expanded `<use>` in place against the referenced element's own transform only, and applied the viewBox mapping of nested `<svg>` and of `<symbol>` instantiated through `<use>`. The root viewBox-to-viewport mapping, including `preserveAspectRatio`, is available as `--space viewport` but is off by default, because applying it multiplies matplotlib output by `4/3` for no semantic reason.
- Skipped geometry that the drawing does not render: `<defs>`, `<clipPath>`, `<mask>`, `<marker>`, `<symbol>`, `<pattern>`, text, images, and anything hidden by `display:none`, `visibility:hidden`, or `opacity:0`. A `<switch>` contributes only its first acceptable child, which keeps Illustrator's "Preserve Illustrator Editing Capabilities" export from emitting its fallback geometry twice. A minimal `<style>` reader resolves `display`, `visibility`, and `opacity` for the universal, tag, `#id`, and single or compound class selectors, so a hidden Illustrator layer delivered as `.st5 { display:none; }` and a CorelDRAW `.fil0.str0` rule are both honored; no other property is parsed, since a geometry converter has no use for the rest.
- Removed points that would round to an identical output row before writing, rather than filtering on a geometric tolerance alone. Curve It's `calculate_polyline_writhe` rejects a zero-length segment outright and `compute_discrete_total_curvature` silently drops the turning angle at one, so the duplicate has to be gone from the file itself: `--points 8000 --precision 1` on the sample drawing previously wrote 5125 zero-length segments and made both calculations fail.
- Wrote closed curves without repeating the first point, matching the convention Curve It, its writhe calculation, and Generate SC already share, and promoted a closed three-point component to four by subdividing its longest edge, since `calculate_polyline_writhe` requires four distinct points and a drawn triangle is legitimate artwork.
- Kept the adaptively flattened points by default, which places a point exactly on every corner. `--points` and `--spacing` resample evenly by arc length instead, keeping exactly every vertex that turns by at least `--min-corner-angle`, 20 degrees by default, and resampling each smooth stretch between corners in proportion to its length. Blind uniform resampling of the sample star to 600 points understated its total curvature by `1.216`; corner pinning reduces that to `0.030`. Resampling additionally flattens sixteen times finer than requested beforehand, because a chord always undercuts the curve it spans and most so where the curvature is highest.
- Flipped the SVG y axis by default, since it points down the page, and documented that the flip is a reflection and therefore reverses the sign of any signed quantity computed from the curve later. Added `--scale`, `--fit-size`, `--center`, `--z`, `--closed`, `--precision`, `--min-points`, `--min-length`, and `--no-split-subpaths`, and `--include`/`--exclude` filters matching a curve's id, class, or enclosing group name, which is how the decoration is dropped from a Plane It projection SVG. Reading back a Plane It projection and dividing by its recorded `data-scale` recovers the original projected coordinates to `5.5e-7` Angstrom.
- Added `-c/--components` for picking curves out of a multi-curve drawing by the labels the listing prints, spelled exactly like Curve It's `--curve-components`: `A`, `B,C`, `A-C`, or `all`.
